# chat-basic-plan.md — building basic instant messaging

**Status (2026-09-29): C1 and C2 implemented; C1b next.** The design is
[DESIGN-CHAT.md](DESIGN-CHAT.md); this document is the order it gets built in,
what each phase delivers, and what proves it.

No media anywhere: page-mode chat touches neither the media layer nor a media
server, so every phase below compiles, runs and is tested with no MCU in the
picture.

## 1. Scope

Basic chat is **objective 1 of the design: a MESSAGE between two subscribers of a
domain, delivered now to every device that is there, and later to the ones that
are not**.

| In v1 | Why it is the floor |
|---|---|
| the `chat` function: `[[domain.chat]]` blocks, first-match on the R-URI user part | MESSAGE is answered 405 today; nothing else in this list is reachable without it |
| the message-layer readings MESSAGE needs (content lifetime, kind of body, device identity) | the rule of one reading in one place ([CLAUDE.md](../../CLAUDE.md), *Message Layer*) |
| the page relay: one MESSAGE fanned out to the AOR's live contacts, one answer back | peer-to-peer chat with every device online |
| the Silo module: store, flush on REGISTER, retention, quotas, shared SQL storage | the recipient offline — the half of objective 1 that needs a module |
| `Kelix.DB.Pool`, extracted from `auth_db` | the Silo is the second SQL client; the design forbids a second copy of the opening logic |
| elixipp page-mode verbs, UAC and UAS | the condition for testing any of this without a node |
| the journal, kelescope and the debug logs show a chat **without its content** | the GDPR constraint: debugging a node must not mean reading its users' messages (C1b) |
| reference scripts, module doc, packaging | a function nobody can install is not shipped |

| Out of v1 | Where it re-enters |
|---|---|
| IMDN generated by the node (RFC 5438) — the `failed` on expiry | the Silo stores the body verbatim, so the request survives storage; generating the notification is a later phase on the same expiry hook |
| push (waking a sleeping mobile) | needs the device-token store of [DESIGN-PRESENCE.md](DESIGN-PRESENCE.md#push-and-the-deferred-invite); the Silo's wake-up window is its other half |
| chatrooms | [DESIGN-CHAT.md](DESIGN-CHAT.md#chatrooms) — a room object, not specified |
| attachments, MSRP, RCS | [DESIGN-CHAT.md](DESIGN-CHAT.md#media) — the URL-versus-MSRP choice is open |
| bots and long-lived conversations | [DESIGN-CHAT.md](DESIGN-CHAT.md#bot) — the `[[domain.chat]]` pattern already routes to a bot script; what the script does is not v1 |
| scale-out as a property of the node | [DESIGN-CHAT.md](DESIGN-CHAT.md#horizontal-scale) — the Silo's storage is shared from day one; the registrar and presence are not |

## 3. Phases

### C1 — the readings, in the message layer

```elixir
SIP.Msg.Ops.message_kind(req)       #=> :im | :is_composing | :imdn
SIP.Msg.Ops.content_expires(req)    #=> 3600 | nil        (Expires on a non-INVITE, §20.19)
SIP.Msg.Ops.instance_id(contact)    #=> "urn:uuid:…" | nil     (+sip.instance, RFC 5626)
SIP.Msg.Ops.device_key(contact)     #=> instance_id, else the contact URI serialized
```

**Delivers** the three questions the Silo and the relay ask of a MESSAGE, each
answered once:

- `message_kind/1` reads the Content-Type, and looks **through** a
  `message/cpim` wrapper (RFC 3862) to the type it carries.
  `application/im-iscomposing+xml` (RFC 3994) is `:is_composing`,
  `message/imdn+xml` is `:imdn`, everything else is `:im`. A typing indicator is
  worth nothing a second later: it is the kind that must never be stored, and a
  script decides that by matching an atom, not by comparing a string;
- `content_expires/1` is **not** `requested_expires/2`: on a MESSAGE, `Expires`
  is the lifetime of the content, there is no Contact parameter and no REGISTER
  default. Absent is `nil`, not a number — the Silo's precedence needs to know
  the sender said nothing;
- `device_key/1` is the identity a delivery is recorded against. It reads
  `+sip.instance` with `get_header_param/2` — a header parameter, never a URI
  one — and falls back to the contact URI, whose duplicate risk the design
  accepts.

**Files** `framework/SIPMsgOps.ex`, `test/msg_ops_message_test.exs`.

**Tests** table-driven, junk included: a CPIM wrapper with no inner Content-Type,
`Content-Type: Application/Im-IsComposing+XML`, a valueless `Expires`, a Contact
whose `+sip.instance` sits inside the angle brackets.

**Done when** each reading answers identically for a parsed and for a hand-built
message.

### C1b — the content stays out of the journal and the logs

**The constraint.** A message's content is personal data (GDPR). Whoever debugs a
node — `kelictl debug`, kelescope's journal popup, a `[log] level = "debug"` —
sees that a MESSAGE went from Alice to Bob, when, over which transport, with which
answer; never what it said. This is not a display option: the content is **never
recorded**, so nothing downstream — the kept journal, its JSON over
`GET /traces/:id`, a PlantUML export, a log file shipped to syslog — can leak it,
and no renderer has to remember to hide it.

```elixir
SIPMsg.redacted(msg)
#=> the same message, the user content of a MESSAGE replaced by
#   "<content not recorded: text/plain, 42 octets>"
```

**Delivers** one function in the message layer, and its two callers:

- **what is redacted**: the body of a MESSAGE of kind `:im` (C1), in or out of a
  dialog — the in-call MESSAGE a B2BUA relays is a message too. Inside a
  `message/cpim` envelope only the **content** goes: the envelope's headers
  (From, To, DateTime, `imdn.Message-ID`) are addressing and timing, the same
  traffic data the SIP headers already show, and exactly what debugging a lost
  or duplicated message needs. The `Subject` header goes with the content: it is
  written by the user. `:is_composing` and `:imdn` bodies are kept — a state and
  a disposition, no text;
- **the journal**: `SIPMsg.readable/1` — what `SIP.Scenario.SipTrace` stores as
  the event's `body` — applies it, so every traced message passes through it
  once, whichever leg or process sent it. The event gains `redacted: true`;
- **the debug logs**: the transports' "Message sent to …" dumps (UDP, TCP, TLS,
  WSS) log `SIPMsg.redacted/1`'s text instead of the raw bytes.

Nothing else in the tree prints a message's body; a grep for the transports'
dump pattern is part of the phase, and a test pins each caller.

**kelescope.** The contract (`kelescope-debug-scenario.md` §4.3) gains
`redacted: boolean` on a `:message` event. A field kelescope does not know is
ignored, so nothing breaks before Part B follows; once it does, the unfolded
message says "content not recorded (GDPR)" instead of showing a placeholder
that reads like a bug. `kelictl debug show --full` prints the same line.

**Files** `framework/SIPMsg.ex`, `framework/SIPTransport{UDP,TCP,TLS,WSS}.ex`,
`dsl/SIPScenarioSipTrace.ex`, `test/message_redaction_test.exs`,
`docs/design/kelescope-debug-scenario.md` (§4.3).

**Done when** a traced call carrying an in-dialog MESSAGE, and a traced chat
instance relaying one, keep journals in which the text appears nowhere — asserted
by searching the stored events for it — while the typing indicator and the IMDN
of the same exchange are shown whole; and a node at `debug` level writes no
message text to its log.

### C2 — the `chat` function

```toml
[[domain.chat]]
pattern = "mybot"
script  = "mybot.exs"

[[domain.chat]]
default = true            # catch-all, must be last
script  = "p2p-chat.exs"
```

**Delivers**, in dispatch order:

- **the framework slot.** `on_message/3` leaves `SIP.Session.Presence` for a
  behaviour of its own, `SIP.Session.Chat`, registered with
  `SIP.Session.ConfigRegistry.set_chat_processing_module/1`; `SIP.Session`
  dispatches MESSAGE into that slot. An elixipp UAS answering MESSAGE must not
  have to pose as a presence server, and presence scripts must stop being the
  place a MESSAGE lands when routing goes wrong;
- **the block.** `Kelix.ChatBlock`, parsed by `Kelix.Domains` with the dial
  plan's rules: ordered, first match on the R-URI user part, `default = true`
  last and single, the same load-time refusals;
- **the route.** `MESSAGE: :chat` in `@method_function`. A domain with no
  `[[domain.chat]]` block keeps its 405 — the path exists today and does not
  change;
- **the advertisement.** MESSAGE joins `Kelix.Options.allow/0`. The list is fixed
  and node-wide, as for SUBSCRIBE, which a domain without presence also answers
  405: `Allow` says what the node can do, the 405 says what this domain does.
  `options_test.exs` is updated in the same commit.

An in-dialog MESSAGE does not pass through here: it reaches its dialog, and the
scenario running the call, exactly as today.

**Files** `framework/SIPSessionPresence.ex`, a new `framework/SIPSessionChat.ex`,
`framework/SIPSession.ex`, `apps/kelixip/lib/kelix/{router,domains,options}.ex`,
`apps/kelixip/test/{router,domains,options}_test.exs`.

**Done when** a MESSAGE for `mybot@domain` reaches `mybot.exs`, one for
`alice@domain` reaches `p2p-chat.exs`, one for a domain without chat gets a 405
carrying `Allow` — and the Linphone typing indicator that once crashed the dialog
is one of the router tests.

### C3 — page-mode verbs

```elixir
uas(:message)

state wait_message do
  on_events do
    {:MESSAGE, _req, _trans, _dlg} -> goto(relay)
  end
end

reply_message(202)                          # UAS: answer the MESSAGE that created us
send_page(to, body, content_type, opts)     # UAC: a new out-of-dialog MESSAGE
```

**Delivers** the two halves elixipp and every chat script need: answering the
MESSAGE that spawned the instance, and sending one that belongs to no dialog. The
outbound MESSAGE is a new non-INVITE client transaction whose answer comes back as
`{:page, :answered, %{code: code}}` or `{:page, :failed, %{reason: r}}` — the
event shape the SBBs use, so a script matches on an outcome, not on a transaction
pid.

`send_MESSAGE` keeps its name and its in-dialog meaning. The new verb is named
differently on purpose: the two build different requests (Route set and tags
versus none), and one name with two meanings is a script that sends out of dialog
what it believed was inside.

The outbound request is **rebuilt**, never replayed: identities, Content-Type,
body and an allowlist of headers (Subject, Conversation-ID, Contribution-ID,
P-Asserted-Identity). The `From` is the sender's, never the node's: a client
files and screens a message by its `From` URI (Trix does both, §6). A `Date`
header is added carrying the **arrival** time when the caller supplies one — the
Silo always does (C6). That rebuilding is a message-layer primitive,
`SIP.MsgTemplate.page_request/2`, because the Silo's delivery (C6) is the same
operation hours later.

**Files** `framework/SIPSessionPage.ex` (new mixin, brought in by
`SIP.Scenario`), `framework/SIPMsgTemplate.ex`, `dsl/SIPScenario.ex`,
`test/page_mode_test.exs`.

The outbound transactions are bound to the scenario in `SIP.Scenario.SipTrace`
as a dialog's are: a traced chat instance shows the MESSAGE it received, the one
it sent and both answers, in one journal — redacted (C1b).

**Done when** a UAC scenario pages a UAS scenario through
`SIP.Test.Transport.Mockup`, both ways, and the request that went out carries no
Via, Route or CSeq of the one it was built from; and a traced instance's journal
holds both transactions.

### C4 — the page relay

```elixir
state relay do
  req = last_uas_req()

  case Kelix.Mod.Registrar.targets(ctx_get(:domain), req) do
    {:ok, peer} ->
      page(args: %{peer: peer, request: req})

      on_events do
        {:page, :delivered, %{code: code}} -> goto(answer, code)          # 200, or 202
        {:page, :refused, %{code: code}}   -> goto(answer, code)          # 603, 415, 403…
        {:page, :unreachable, _}           -> goto(store, "no device took it")
      end

    :notfound -> goto(store, "nobody registered")
  end
end
```

**Delivers** `SBB.Page`, the building block that answers the question the design
leaves open — *what a chat B2BUA is*. It is not the two-leg machinery of a call:
there is no dialog to bridge, no BYE, no re-offer. It is **one inbound
transaction, N outbound transactions, one answer**:

- the request is rebuilt (C3) and sent to **every** contact in `peer` in
  parallel, not hunted serially — RFC 3428 §8 lets a proxy fork a MESSAGE, and
  every modern client expects it on every device;
- a 2xx is `:delivered`, and **the code is kept**: a 200 from any device wins at
  once; 202s alone give a 202 once every transaction has ended. A device's 202
  says *accepted, not delivered* — Trix answers it for an unknown sender it puts
  in quarantine (§6) — and the relay does not upgrade it into a 200 the
  recipient never gave;
- no 2xx splits in two, and the split is the SBB's, not the script's, because
  it is a reading of SIP codes:
  - **`:refused`** — at least one device gave a final verdict on the *content or
    the sender*: 403, 415, 488, 603, 606. The best one is relayed back. Storing
    it would be wrong twice over: a blocked sender's message would come back at
    every REGISTER, a 415 would be refused at every flush;
  - **`:unreachable`** — every failure says *not now*: 408, 480, 500, 503,
    transport error, timeout. This is what the Silo is for;
- `:is_composing` is never stored: a script that gets `:unreachable` for one
  answers 480 and stops. That line is in the reference script, and C1 is what
  makes it one line.

The contacts the relay reached are handed back in the outcome as device keys (C1):
the script passes them to the Silo when it stores, so the devices that already
have the message are never served it a second time by a flush.

In the journal, each device's transaction is a lane of its own (its own
Call-ID) labelled with the device, so kelescope draws the fan-out as it happened:
which device answered what, and which one never did.

**Files** `dsl/sbb/page.ex`, `test/sbb_page_test.exs` — one Mockup peer per
device (`;unittest=alice-phone`, `;unittest=alice-desk`).

**Done when** two devices of which one answers 200 and one 480 give the sender a
200, one 202 and one 480 give a 202, one 603 and one 480 give `:refused` with the
603, three 480s give `:unreachable`, and a device that never answers does not
delay the 200 the other one earned.

### C5 — `Kelix.DB.Pool`

**Delivers** the opening logic of `Kelix.Mod.AuthDb.Pool` — driver resolution,
TLS negotiation, backoff, the common option set, `describe/0` — as a module both
SQL clients start under a name of their own:

```elixir
Kelix.DB.Pool.child_spec(config, name: Kelix.Mod.AuthDb.Conn)
Kelix.DB.Pool.child_spec(config, name: Kelix.Mod.Silo.Conn)
```

`auth_db` changes nothing it exposes: its block, its account and its pool name
stay. An optional `[database]` block in `config.toml` supplies defaults both
module blocks inherit; a module block wins key by key. The code is shared, the
connection never is ([DESIGN-CHAT.md](DESIGN-CHAT.md#horizontal-scale)).

This phase changes no behaviour, and that is its test: the whole `auth_db` suite
passes unchanged, and `kelictl` shows the same descriptor.

**Files** `apps/kelixip/lib/kelix/db/pool.ex` (in the core: a pool is not a SIP
function), `apps/kelix_modules/lib/kelix/mod/auth_db/pool.ex` reduced to its
configuration, the tests moved with the code.

### C6 — the Silo module

```elixir
Kelix.Mod.Silo.store(sip_ctx, req, served: devices, retention: 120)
#=> {:stored, %{id: id, expires_in: 120}} | {:error, :quota} | {:error, :down}

Kelix.Mod.Silo.flush(sip_ctx, req)        # after the 200 to a REGISTER
#=> :ok                                    # asynchronous: delivery is not the registrar's time
```

**Delivers** store-and-forward as specified in
[DESIGN-CHAT.md](DESIGN-CHAT.md#the-silo-module), in this order:

1. **the schema**: one table of messages, one of devices served, DDL for
   MariaDB/MySQL and for PostgreSQL shipped under `packaging/sql/silo/`, a
   version row. The module checks it at start and **refuses to start** on a
   missing or stale schema; it never runs DDL;
2. **store**: the retention is the sender's `content_expires/1`, else the
   script's `:retention`, else the domain default — bounded by the domain
   maximum. Per-AOR count and size quotas; exceeding one is `{:error, :quota}`
   and the script picks the code. The body is stored **verbatim**, CPIM wrapper
   included, so an IMDN request survives storage untouched;
3. **flush**: read the AOR's pending messages, claim them with the conditional
   `UPDATE … WHERE claimed_by IS NULL` and an expiring lease — **the AOR's
   backlog as one batch, not message by message**, so one node delivers all of it
   and in order — rebuild with
   `SIP.MsgTemplate.page_request/2` — `Date` set to the arrival time, body
   untouched, no "offline message" prefix — and send to each present contact
   whose device key is not in the served set. The answer is read with the
   classes of C4: `:delivered` and `:refused` both add the device to the served
   set (a device that said 603 or 415 once will say it again), `:unreachable`
   leaves it out for the next flush. Release the lease. Flushing is local to the
   node that received the REGISTER; nodes meet through the rows.

   **Delivery is in arrival order, one message at a time per device.** Page mode
   carries nothing a client could reorder by: every MESSAGE is a transaction of
   its own, with a new Call-ID, so CSeq says nothing across two of them, and a
   client that uses neither CPIM `DateTime` nor `Date` — Trix sends `text/plain`
   and files by reception time when `Date` is absent — shows messages in the
   order they reach it. So, per device, message *n+1* leaves only once *n* has
   its final answer, and an `:unreachable` answer stops that device's queue for
   this flush: sending *n+1* after a lost *n* would deliver them out of order at
   the next one. Devices are served in parallel with each other; order is a
   property of one device's view, not of the AOR. The `Date` the Silo sets is
   the second line of defence, for the clients that read it;
4. **the index**: a positive-only ETS cache of "this AOR has pending messages",
   so a REGISTER for an AOR with nothing stored costs no SQL round trip;
5. **the sweep**: expired messages deleted on a timer; each one never delivered
   to any device increments `kelix_silo_expired_undelivered_total{domain}` — the
   metric that betrays a registrar script which forgot to call `flush`;
6. **the control surface**: `kelictl silo list <aor>`, `kelictl silo purge
   <aor>`, the counters in `kelictl status`. The list shows **metadata only** —
   sender, arrival, expiry, size, content type, devices served — never a body
   (C1b): the operator purging a queue does not need to read it;
7. **what a flush leaves for debugging**: a delivery runs in the module, not in a
   scenario, so it has no journal. It leaves one `info` line per attempt — AOR,
   device key, stored message id, answer — and the counters. The flush is
   *started* from the registrar script, whose journal shows the `flush` call;
   linking that to the delivery lines is the stored message id.

### C8 — kelixip

**Delivers**

- `scripts/p2p-chat.exs`: authenticate (the rule of `auth_db.challengeable?/1`
  already covers MESSAGE), 404 for an AOR that does not exist, relay (C4), store
  on `:undelivered` and answer **202**, answer 480 for an undelivered
  `:is_composing`, 503 when the Silo is down. A MESSAGE sent **inside an
  established dialog** is never re-challenged (see *Decisions*);
- `scripts/registrar-chat.exs`: `registrar-presence.exs` plus `Silo.flush` after
  each 200 that leaves the AOR registered. A variant, as `registrar-presence.exs`
  is one of `registrar.exs` — see *Decisions*;
- `docs/kelixip/modules/silo.md`, in the register of `mcu.md`;
- the `kelixip-mod-silo` package (RPM and deb), shipping the `.beam` and the two
  DDL files;
- `packaging/config/config.toml`: a commented `[[domain.chat]]` and
  `[module.silo]` example.

**Recipe** two clients on one domain, one Linphone and one Trix, then two Trix:

1. Alice pages Bob online on two devices (both receive, Alice sees one 200);
2. Bob quits, Alice pages him (202); Bob restarts: the message arrives after his
   200 OK, once per device, filed by Trix at its `Date`;
3. Trix's tab is frozen (`edge://discards`) and woken, twice: the message
   arrives once, not at every wake-up (§6, the `+sip.instance` point);
4. Bob has blocked Alice in Trix: her page gets 603 and nothing is stored;
5. an unknown sender pages Trix: 202 relayed back, nothing stored;
6. Linphone's typing indicator reaches Trix (415 back) and is never stored;
7. the `p2p-chat.exs` instance of step 1 is journalled from kelescope: the
   fan-out is readable lane by lane, and no message text appears in the popup,
   in `kelictl debug show --full`, nor in the node's log at `debug` level.

The Kamailio `msilo` recipe of Trix's ADR 0008 §5 is the same list; kelixip
replaces its proxy, and `docs/utilisation/deploiement.md` in trix-web-client
gains the kelixip configuration beside the Kamailio one.

## 4. Decisions this plan takes

1. **A chat relay is `SBB.Page`, not a B2BUA leg.** The design leaves the term
   open. The answer taken: one inbound transaction, a parallel fan-out, one
   answer. The B2BUA's leg machinery accepts a MESSAGE today, but a leg carries a
   dialog, a teardown and a media plane — none of which a page has — and it hunts
   serially where a page must reach every device at once.
2. **MESSAGE gets a framework slot of its own.** `on_message/3` leaves
   `SIP.Session.Presence`. The Router's comment promised that the callback would
   not change when chat landed; it does not — only the behaviour declaring it
   moves.
3. **MESSAGE is advertised node-wide.** `Allow` describes the node, the 405
   describes the domain; SUBSCRIBE already works this way.
4. **The sender's answer is 200 when a device took it, 202 when the Silo did —
   or when the only devices that answered said 202 themselves.** RFC 3428 §7
   makes 202 the answer of a server that accepted a request it has not
   delivered; a client that shows "delivered" on 200 and "sent" on 202 then
   shows the truth. A refusal (`:refused`, C4) is relayed, never stored.
5. **The body is stored verbatim.** The design's header allowlist applies to SIP
   headers; the CPIM wrapper is the body, and its IMDN fields go with it.
   Generating IMDNs is left out of v1, reading them costs nothing.
6. **The flush lives in a registrar variant, not in `registrar.exs`.** Declaring
   `:silo` in `registrar.exs`'s `uses_modules` would stop every node without chat
   from loading its registrar. The price is one more variant — acknowledged in
   *Risks*.
7. **An in-dialog MESSAGE is not re-challenged.** The dialog was authenticated
   when it was created; a challenge mid-dialog proves nothing new and breaks
   clients that do not expect one. This holds for the MESSAGE a UA sends in the
   dialog its first page opened, which reaches the `p2p-chat.exs` instance
   still serving it, and for one sent inside a call. The rule is
   `Kelix.Mod.AuthDb.challengeable?/1`'s, which already excludes in-dialog
   requests; the script asks it and does not re-derive it, and C8 carries a test
   in which a second MESSAGE in the same dialog is relayed with no 401/407.
8. **A message's content is never recorded outside the Silo, and this is not
   configurable.** Not a filter in kelescope, not a flag an operator can turn
   off while debugging: a switch that reveals the content is a switch someone
   leaves on, and the journal it filled is kept for an hour and exported as JSON.
   The Silo holds content because delivery needs it — that is its purpose, its
   retention is bounded, and nothing reads it but the delivery. Redaction lives
   in the message layer for the reason every reading does: one place decides what
   a MESSAGE's content is (C1b).
9. **The storage is SQL from the first commit.** No in-memory Silo is shipped:
   the in-memory store exists for the test suite only. A node that loses its
   messages on restart has already answered 202 to their senders.

## 5. Order, and what runs in parallel

C1 → C3 → C4 is the spine of peer-to-peer chat with everyone online. **C1b
comes before C3**: the first phase that makes a node carry MESSAGEs is the last
moment their content can be kept out of a journal by construction rather than
cleaned out of one afterwards. C2 depends
on nothing and can start first. C5 depends on nothing either, and is best merged
early, while `auth_db` is quiet. C6 depends on C1, C3 and C5. C7 depends on C3.
C8 depends on everything.

**Two release points.**

- **1.7.0** — C1 to C4, C7, and C8 without the Silo: page-mode chat between
  registered devices, 480 when nobody is there. Useful on its own, and it
  exercises the dispatch and the relay on real clients before the store is built
  behind them.
- **1.8.0** — C5, C6 and the rest of C8: offline delivery.

1.7.0 is not enough for a client that unregisters while asleep: Trix's
correspondents get 480 for as long as its tab sleeps (§6). A Trix deployment on
kelixip starts at 1.8.0.

Each is a minor (a new SIP function, then a new module), and the number lives in
the places [CLAUDE.md](../../CLAUDE.md) lists — four manifests (one of them
twice), two User-Agent defaults, two spec files with `Release:` back to 1, and a
deb changelog entry.

## 6. What Trix expects

Trix (`../trix-web-client`, ADR 0008, implemented 2026-09-29) is the first
client written against this server, and its deployment guide already states
what it requires of one. Cross-checked against its code (`src/sip/message.ts`,
`src/sip/port.ts`) on 2026-09-29:

| Trix does | What it asks of this plan | Where |
|---|---|---|
| unregisters when the browser puts the tab to sleep (ADR 0006), and calls server-side storage a **deployment requirement** (D8) | offline delivery is not optional for Trix: 1.7.0 alone answers its correspondents 480 while it sleeps | §5 — Trix needs 1.8.0 |
| sends and accepts `text/plain` only; anything else is **415** with `Accept: text/plain` (D1) | a 415 is a refusal, not an absence — never stored, never retried | C4, C6 |
| answers **603** to a blocked sender (D7) | same: storing it would bring the blocked message back at every wake-up | C4, C6 |
| answers **202** to an unknown sender and keeps the message in a local quarantine (D5) | the relay passes the 202 on unchanged | C4, decision 4 |
| answers **480** when its messaging link is not open | unreachable, stored | C4 |
| files a deferred message at its `Date` header when present and not in the future, otherwise at reception (D8); asks msilo for `add_date = 0` | the Silo sets `Date` to the arrival time and never touches the body | C3, C6 |
| classifies the sender by the `From` URI, never the display name (D4) | the rebuilt request keeps the sender's `From` | C3 |
| has no de-duplication at all, and no automatic retry (D3) | every duplicate the node produces is shown twice to the user | below |
| sends every message out of dialog (`ua.sendMessage`), each with a new Call-ID | each Trix MESSAGE is an initial request and is challenged; decision 7 never applies to it — it applies to clients that reuse a page-mode dialog | decision 7 |
| answers **501** to a MESSAGE inside a call dialog (D10) | a call script relaying MESSAGE in-dialog towards a Trix leg gets 501: expected, not a bug | — |
| reads 405 or 501 on a sent MESSAGE as "this server does not route messages" and closes the writing field (D13) | a domain without `[[domain.chat]]` answers 405 — exactly the signal Trix expects | C2, decision 3 |
| caps a body at 1000 UTF-8 bytes (D2) | nothing: well under the Silo's quotas | — |
| does not see what the same account sent from another device (D9) | a "carbon" copy to the sender's other devices is a server feature, and it is not v1 | §1, *Out of v1* |

**The one point that breaks the Silo as designed: `+sip.instance` is not stable
in Trix.** JsSIP writes `+sip.instance="<urn:uuid:…>"` on every Contact, from
the UA's `instance_id`, and generates a new UUID when none is configured. Trix
configures none, and builds a new UA each time it starts — every page load and,
per ADR 0006, every wake-up. To the Silo, each wake-up is a **new device**: the
served set does not recognise it, and since a message is never consumed
([DESIGN-CHAT.md](DESIGN-CHAT.md#multi-device-fan-out-at-delivery-not-at-storage)),
every message still in retention is delivered again, at every wake-up, to a
client that cannot tell it has seen it before.

The fix is on Trix's side: generate the UUID once per account and per device,
keep it in the vault (`StoredAccount.instanceId`, not in `AccountConfig`, so a
share link does not carry it to a second device), pass it as `instance_id`.
RFC 5626 §4.1 requires exactly that — the instance ID is persistent across
restarts of the same UA. **Done in trix-web-client on 2026-09-29** (branch
`feat/im`); C8's recipe step 3 is what proves it in the field. The Silo does not grow a workaround (a per-AOR "delivered
to someone" flag would reintroduce the consumption the design refused, and lose
the second device).

## 7. Risks

- **registrar variants multiply.** `registrar`, `registrar-presence`,
  `registrar-chat`: the next function wanting a hook on REGISTER makes it four,
  and presence without chat is already one combination the reference set does
  not cover. The fix is a registrar SBB whose hooks a script composes; it is not
  v1, and this line is here so the fourth variant is not written without it.
- **a forgotten `flush` fails silently.** The metric of C6 is the only guard, and
  a metric nobody graphs guards nothing: the module doc says which alert to set.
- **a client with an unstable `+sip.instance` gets every retained message at
  every registration.** Trix was one until 2026-09-29 (§6); any client that regenerates its
  instance ID behaves the same. The served set cannot tell, so C8 logs a warning
  when one AOR registers more distinct device keys within a retention period than
  its binding limit allows.
- **two reference clients, and they disagree on formats.** Linphone sends CPIM
  and `isComposing`; Trix accepts `text/plain` alone and answers 415 to both. A
  Linphone → Trix message fails with a 415 relayed back, and v1 does not unwrap
  CPIM on the way — that is a format conversion, and it belongs to the CPIM/IMDN
  phase on both sides.
- **a live message can overtake the backlog.** A MESSAGE arriving while a flush
  is still running is relayed to the device at once (C4), and may reach it before
  the older stored ones. The window is the length of one flush. Queueing live
  traffic behind the Silo would close it at the cost of making every message
  to a just-registered AOR wait for SQL; v1 accepts the window, and the stored
  messages carry their `Date` for the clients that read it.
- **the lease is the one concurrent path.** A node dying mid-delivery leaves
  messages claimed until the lease expires; a lease too short delivers twice to
  a slow device. The default is set from C8's measurements, and the served set
  bounds the damage to one duplicate per device.
- **content can leak by another path than the two C1b covers.** A script that
  logs `last_uas_req()`, a scenario printing a body in a failure reason, an
  `inspect/1` of a request in an error log. The reference scripts are written not
  to; the module doc says why a customer's script should not either. A crash
  report carrying a request in its state is the hard case: the Logger formatter
  is where a last-line redaction would go, and it is not v1.
- **other personal data in the journal.** A PIDF `<note>` is written by the user
  too, and the journal shows it today. The constraint as stated is about
  messages; extending C1b's rule to presence notes is one clause in the same
  function, and a decision for the presence side.
- **the SQL tests are gated.** A suite that is green without a database proves
  the logic, not the dialects. The release checklist for 1.8.0 runs both gates
  against real engines once.
